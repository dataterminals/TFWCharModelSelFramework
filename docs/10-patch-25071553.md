# Build 25071553 — what the patch did to CMSF, and what is still unknown

**STATUS 2026-09-09: every static check CMSF has passes against the live build. The two gates that
could still explain the field report both need the game launched, and neither has been.**

The short version for anyone picking this up cold. A player report says the framework pak breaks
their game and that the selector never unlocks. The obvious suspect was staleness — v0.2.4 ships a
pak built from the **2026-07-21** cook, and the game is now four announced versions later. That
suspect has been measured and it does **not** hold up: the pak reverts nothing, pins nothing dead,
and its copies of the overridden assets differ from the live ones by 2–23 scalar bytes apiece,
at identical length. So the cause is
somewhere this repo cannot currently see, and the honest position is that CMSF is **unverified on
this build**, not broken by it.

Do not ship a rebuild off the back of this document. See "Why nothing was rebuilt".

---

## The report

DM, 2026-09-09, from a player who installed CMSF to use a Scav Girl skin:

> It works, but only without the .pak/.ucas/.utoc files. However, it still doesn't unlock the menu
> for the characters that are supposed to have a selection option — specifically, the one I
> installed the mod for (Scav Girl).

Two claims, and they are separable:

1. **the pak trio is not survivable** — the configuration only works with `CMSF_Core_9_P.*` removed
2. **the selector does not unlock** — even in that pak-less configuration, Scav Girl's menu does
   not gain its base skins

Claim 2 in a pak-less install is `CMSFUnlock` alone, which is the half that does not need the pak.
Claim 1 and claim 2 therefore have *different* suspects and should not be chased as one bug. A
third reading is possible and cannot be ruled out from the text: that "it works" means the game
runs, and both halves are simply failing.

## What was measured, and what each measurement is worth

Ordered by how much weight it can carry. The first three read no type map and are the load-bearing
ones; see "Why nothing was rebuilt" for why that distinction matters this cycle.

### 🟩 The frozen ABI is intact — `grep -c "^ForeverWinter/Content/CMSF/"` returns **0**

The one check in this repo that guards *other people's* paks. The developers have not collided
with the slot namespace, so every claimed third-party slot in the wild is still addressable. This
is filelist-only, so it is as solid as it gets.

### 🟩 Nothing CMSF owns or reads has moved

Every path is present at its exact spelling in the 76,321-entry live filelist: `DT_SkinUIData`, all
six `BP_Player_*`, `ST_FW_UI_Skins`, `WBP_SkinSelection`, `WBP_SkinButton`,
`WBP_PlayerStatusWidget`, `WBP_MenuMaster`, `WBP_ReadyRoom`, `GA_Player_ChangeSkin`,
`DT_Entitlements`, `DT_EntitlementTags`.

This matters most for `CMSFUnlock`, whose documented failure modes are all *renames* that fail
silently — the claim signal returning nil, or `Init()` disappearing. At the asset level, none of
them fired. It does **not** clear the runtime members (`SelectLockedSkinsOnly`, `Init`,
`SkinOptions`, `SkinRow.RowName`, the `SkinIcon.Brush.ResourceObject` chain), which live inside
those assets and cannot be checked without running the game.

The filelist diff is 153 added / 142 removed and is mostly **directory-case churn**
(`Posed/`→`posed/`, `DataLayers/`→`Datalayers/`, `images/`→`Images/`, `TOOTHY/`→`Toothy/`,
`Bagman/`→`BagMan/`). Benign: UE lowercases the package name before hashing `FPackageId`.

### 🟩 The shipped pak's overridden assets differ from live by 2–23 scalar bytes

The strongest result here, and the one that killed the staleness theory. `retoc to-legacy` takes
**no usmap**, so this is a raw byte comparison of the game's own asset, July cook versus September
cook, and it is immune to the type-map problem below.

Full result, now automated as `verify_build.sh` check [5] — **6 of 14 files drifted**:

| asset | `.uasset` | `.uexp` |
|---|---|---|
| `BP_Player_BagMan` | identical | **3** bytes differ, same length |
| `BP_Player_Girl` | identical | **7** bytes differ, same length |
| `BP_Player_Gunhead` | identical | **23** bytes differ, same length |
| `BP_Player_MaskMan` | identical | **3** bytes differ, same length |
| `BP_Player_OldMan` | identical | **2** bytes differ, same length |
| `BP_Player_Shaman` | identical | **3** bytes differ, same length |
| `DT_SkinUIData` | identical | **identical** |

Every `.uasset` header is byte-identical, every `.uexp` is the **same length**, and
`DT_SkinUIData` did not change at all. That rules out the failure class everyone reaches for
first: the pawn Blueprints were not restructured, no export was added or removed, and the
July-cooked copies are not a structural mismatch for the September loader. What the stale pak
*does* revert is a handful of tuning scalars per pawn — real, worth fixing by rebuilding, and not
a crash. Gunhead's 23 is the largest and is consistent with the patch-notes line about its head
weapon aiming.

> **A trap worth recording.** Decoding the pak's `BP_Player_*` and diffing the JSON against the
> live base makes each shipped copy look ~25% *smaller*, which reads as "the pak deletes a quarter
> of the Blueprint". It is an artifact. `verify_build.sh` mounts an override pak **alone** on
> purpose, so five component classes (`BPC_Stamina_C`, `BP_AC_HealthSFX_C`,
> `BP_AC_PlayerAimingSFX_C`, `BP_AC_PlayerSprint_SFX_C`, `BP_AC_Rig_SFX_C`) cannot resolve and
> decode as bare `UObject` with empty properties. The script's own header calls this out as a
> documented gap. Byte-compare through `retoc`; do not JSON-diff across an isolated mount.

### 🟩 `verify_build.sh` is clean against the live build

Run in full, exit 0:

- **0 dangling soft references** across 791 references in 199 dumps, for both the framework pak and
  the octogirl author pak. Every mesh and portrait path the frozen overrides pin still resolves.
- **Group 1 reversion check: 0 rows, soft paths or roster entries dropped.** Live `DT_SkinUIData`
  has **33 rows**; the pak carries all 33 plus 192 CMSF rows. `SkinChoices` goes base→base+32 on
  every character. **The developers added no skin rows and no roster entries this cycle**, so the
  staleness inversion did not fire.

Live Scav Girl roster, for reference: `SkinChoices` = 5 (`SK_SCV_FL` … `SK_SCV_FL4`),
`LockedSkinChoices` = 3 (`SPT`/BlindFang, `DEC`/Dec2025, `DSQ`/April2026). So **8** available
unfiltered, where `docs/00-findings.md` recorded 7 — one entitlement skin was added at some point.
Worth updating the "vanilla unfiltered Scav Girl is 7" field check in
`tfw-update-ops/state/asset-dependencies.md`, which is now off by one.

> Note `DT_SkinUIData` carries a row `Skin.Girl.MAY` pointing at
> `Female/Skins/MAY/SK_SCV_FL_May`, and that mesh is in **neither** of Scav Girl's roster arrays.
> A row without a roster entry does not appear — that is the game's own unfinished content, not

### 🟩 Pak mods in general are fine on this build

Not a CMSF measurement, but it bounds the problem. A weapon overhaul shipped to Nexus on 2026-09-06
and several inventory/stat paks were updated 09-05, all without breakage reports; another modder
confirms a pak mod working "two updates early". Whatever is happening to this player, the game is
not rejecting third-party paks wholesale, and `FWPakManifest.json` — which enumerates only the base
containers, with a signature over that list — is not gating `Content/Paks/Mods/`.

## The two gates that are still shut, and both need a launch

### 🟥 Gate 1b — the usmap is stale, and it fails silently

Measured on the `FWWeaponDefinition` export of `DA_WPN_PLAYER_HRF01`, same extraction three ways:

| decode | properties |
|---|---|
| build `24536482` with its own correct map | **57** |
| the baseline's kept `-STALE-USMAP` sample | 30 |
| **build `25071553` with the current map** | **30** |

57 is the exact number `provenance.json` records as this map's verification, and gate 1b's note in
`status.md` says it "was stopping at 30" before the last regeneration. It is stopping at 30 again,
with no error and plausible-looking values. `bConvergeADSAimToCamera` reads at index 28 of 30
instead of index 46 of 57 — the "real bytes under neighbouring property names" symptom, not a sign
of health.

This does not touch any 🟩 above. It does block the fix.

### ⬜ Gate 3 — `CMSFUnlock` has never run on this exe

There is no `UE4SS.log` anywhere under `D:\MO2_InstanceData\TheForeverWinter`. The game has not
been launched under MO2 since 2026-08-04. So:

- whether UE4SS `-894` still attaches to a September binary is **unattempted, not merely unscored**
- whether `SelectLockedSkinsOnly`, `Init()` and the claim-signal chain still resolve is unknown
- the v0.2.4 forced-repopulate path has never been exercised against this build

Claim 2 in the field report lives entirely behind this gate. Note also that Root Builder's cache
is keyed on the engine version (`5_4_2_0`), unchanged since July, and has had no chance to rebuild
against `25071553` — so **the revert mechanism is armed for the next launch.** Clear
`GameData.json` and its sibling `Backup\` together *before* launching, or the measurement session
will be taken on a partially-July install.

## Why nothing was rebuilt

Doctrine says rebuild the framework pak unconditionally after every patch, and that is still the
right move — the byte diff shows a few reverted tuning scalars that a rebuild recovers, and
re-basing on the current cook is cheap insurance.

It was not done here because **`cmsf_framework.py` serializes through `skinpatch`/UAssetAPI against
the usmap**, and that map is demonstrably wrong for at least one struct family on this build. A
rebuild against it could silently mis-serialize `DT_SkinUIData` or the six pawn Blueprints and
produce a pak that passes every check in this repo while being wrong in-game — which is the exact
shape of the two failures this project has already shipped. Stage 1 gates Stage 5 for a reason.

**Order of operations to actually fix this:**

1. Regenerate the usmap (experimental UE4SS → `DumpUSMAP()`, then remove UE4SS). Archive the
   outgoing `24536482` map and update `provenance.json` in the same commit.
2. Re-run `bash tools/verify_build.sh` against the fresh map — the reversion numbers above were
   taken with the stale one, and although a relative comparison across an identical map is fair,
   they are worth re-establishing before anything ships.
3. `python tools/cmsf_framework.py --slots 32` to rebuild on the `25071553` cook.
4. Launch and read the log. The fastest single field check is `cmsfunlock`'s
   `selector lists N skin(s)` at Scav Girl: **8** means unfiltered vanilla (not 7 any more),
   **40** means the framework is loaded and populating. **0** means the panel read failed.
5. Only then package and ship.

`FW_AES_KEY` is required for step 3 and is not in this repo by design. The key is embedded in
`forever-winter-datamine/datamine/decoder/Program.cs` and is noted there as constant across
patches; supply it via the environment and do not commit it here.

## What to ask the reporter for

Nothing measured so far reproduces claim 1, so the next move is their diagnostics rather than more
static analysis. In priority order:

1. **`UE4SS.log`.** Settles gate 3 for their machine in one file — whether UE4SS attached, whether
   `CMSFUnlock` loaded, and which version banner it printed (`v0.2.4 loaded — …`).
2. **What "breaks" means with the pak installed** — crash on launch, crash entering the hub, black
   character, missing character, or the menu simply staying empty. These have different causes and
   the report does not distinguish them.
3. **The exact install layout**, verbatim paths. `CMSF_Core_9_P.{pak,ucas,utoc}` belongs in
   `Windows\ForeverWinter\Content\Paks\Mods\`, and `CMSFUnlock` under
   `Windows\ForeverWinter\Binaries\Win64\ue4ss\Mods\CMSFUnlock\` with its `enabled.txt` — **not**
   as a pak mod. That specific mistake has already been the answer once in the TFW Discord.
4. **Which Scav Girl skin mod**, and whether it is a CMSF slot pak or a conventional
   package-identity overwrite. An overwrite skin and CMSF are not the same product and do not need
   each other; if theirs is an overwrite mod, the framework pak is not what makes it appear and
   removing it is correct.
5. **UE4SS build.** `CMSFUnlock` is developed against experimental `v3.0.1-894-g2172883`. A stable
   release may load the Lua and still not expose what the mod reads.
6. Whether any other pak mod is installed that touches player characters.

## Loose ends this cycle turned up

- ~~**`verify_build.sh` cannot see whole-asset drift.**~~ **Fixed this cycle.** It compared only
  rows, soft paths and roster entries, so the scalar reversion above passed as "clean". Check
  **[5] cook drift** now byte-compares each overridden asset — live cook versus
  `build/framework/src`, the pristine extraction the pak was built from — through
  `retoc to-legacy`, which is passed **no usmap** and is therefore the one check here that still
  works when gate 1b is red. It is opportunistic: missing retoc, `FW_AES_KEY` or the local build
  tree is a SKIP that is carried into the RESULT line, never a silent pass. Drift is reported and
  surfaced in RESULT but does **not** set the exit code — a drifted cook means a rebuild is owed,
  not that the pak is broken.
- **`docs/00-findings.md` and `asset-dependencies.md` say "unfiltered Scav Girl is 7".** It is 8
  on this build. Small, but it is the documented field check.
- **The Shaman MAY material renames** are direct exposure for `forever-winter-skin-mods`, not for
  CMSF. Routed to that repo's owner via the ops board rather than handled here.
