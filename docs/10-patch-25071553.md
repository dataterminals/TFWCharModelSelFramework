The short version for anyone picking this up cold. v0.2.4 ships a pak cooked **2026-07-21**; the
game is now four announced versions past that. The first suspect was *content* staleness — that our
whole-asset override deletes developer changes — and that suspect is dead: the pak reverts nothing,
pins nothing dead, and its copies of the overridden assets differ from live by 2–23 scalar bytes at
identical length.

**The pak does crash the game, but the reason proposed below is wrong.** ~~A zen container resolves
its script imports through the game's global script-object store, and that store changed:
3,012,295 bytes at the July cook, 3,017,553 today.~~ The store change is additive and provably
inert — see [`11-container-staleness-refuted.md`](11-container-staleness-refuted.md). The crash
cause is open, and the leading untested candidate is `PackageImport` **public-export-hash**
staleness, which is a different mechanism from the script store.

The lesson that does survive: **content equivalence is not survivability.** The seven owned assets
can be byte-for-byte fine and the container still fail to load — that framing was right, and only
the specific mechanism was wrong.

### P1: the arithmetic already in this repo corroborates PinoIsReading

This costs no launch and no usmap, and it was sitting in `00-findings.md` since July. That file's
live measurement of the selector reads:

| `SelectLockedSkinsOnly` | selector shows | composition |
|---|---|---|
| `true` (default) | 2 entries | owned `LockedSkinChoices` only |
| `false` (cleared) | 7 entries | 5 `SkinChoices` + 2 owned locked |

Scav Girl's `LockedSkinChoices` array is **3** long. The default filter showed **2**. So the filter
does not feed on the array — it feeds on the **owned subset of** the array, and the difference
between 3 and 2 is one skin this account is not entitled to.

Run that forward over the per-character roster (`SkinChoices`/`LockedSkinChoices`):

| character | `SkinChoices` | `LockedSkinChoices` | default selector, account owning **none** |
|---|---|---|---|
| BagMan | 4 | 1 | **0** |
| Girl | 5 | 3 | **0** |
| Gunhead | 1 | 3 | **0** |
| MaskMan | 3 | 3 | **0** |
| OldMan | 2 | 2 | **0** |
| Shaman | 1 | 3 | **0** |

Every character defaults to a selector fed **zero entries** on an account with no skin entitlement
for them. That is PinoIsReading's report, arithmetically, with no new mechanism required — and it
explains the MaskMan exception exactly, since a skin given free to everyone is *owned* by every
account and makes his the one non-empty set.

**The limit, which is the whole open question.** This establishes that the selector is fed nothing.
It does **not** establish that the panel is absent. `00-findings.md` measured a panel that existed
and showed 2; nobody has measured one at 0. Two possibilities remain and they need opposite fixes:

- **Constructed but empty.** Then clearing `SelectLockedSkinsOnly` — what `CMSFUnlock` already
  does — should be sufficient, and v0.2.4's forced-repopulate path is the right shape of fix.
- **Never constructed.** Then there is a second gate upstream of the filter, and no amount of
  unfiltering reaches it.

**Sigfried's 2026-08-19 report is the discriminator and it points at "never constructed"** — it
came *after* v0.2.4, so the forced repopulate ran and the menu was still absent. That is inference
from one report, not a measurement, so it ranks the two rather than settling them.

⚠ **This makes doc-10's own field check ambiguous.** "**0** = the panel read failed" is not safe:
on an unentitled account, 0 is also the *correct* reading of a panel that is working exactly as the
game intends. See the corrected check under "Order of operations" below.

**Three things were being conflated, and separating them is the finding:**

1. **The widget is always constructed.** `CMSFTime` logged `WBP_SkinSelection_C` built for all four

player is considered to own. **Which of those is reachable from UE4SS Lua is the next question**,
and it is a different mod surface from anything `CMSFUnlock` currently does.

## P0 — the mechanism proposed here is REFUTED (kept as the record of a wrong turn)

> Superseded by [`11-container-staleness-refuted.md`](11-container-staleness-refuted.md), which
> carries the measurements. Kept verbatim below because the reasoning error — treating a size delta
> as evidence of breakage, then rescuing the hypothesis with an invented exposure asymmetry when
> counter-evidence arrived — is the instructive part. The 220-of-220 resolving ScriptImports killed
> it outright.

Every check here mounts the pak **alongside the live `global.utoc`/`global.ucas`**, because a mod
pak has no ScriptObjects chunk of its own and cannot be read without one. That is necessary, and it
is also precisely why the crash is invisible: the checks supply the very global store the shipped
pak disagrees with, then confirm the content is fine. It is.

The store itself moved:

| | bytes |
|---|---|
| `scriptobjects.bin` extracted at the **July** cook (what v0.2.4's pak was packed against) | 3,012,295 |
| `scriptobjects.bin` extracted at the **live** cook | 3,017,553 |

**+5,258 bytes of new script objects.** A zen container serialises its imports of native classes,
functions, properties and structs as references into that global store; `retoc to-zen` resolves
them at pack time. Change the store and a pre-existing container's script imports no longer denote
what they did. The six pawn Blueprints are dense with such imports, and `BP_Player_*` is loaded
while the player character is constructed — at launch.

The timing corroborates it. `0.9.5.0` (2026-08-28) is the "ground-up combat AI overhaul", a new AI
state machine plus a client-side shooting rework — the kind of change that adds native classes and
therefore script objects. Every crash report dates to `0.9.5.0` and none to the three subsequent
hotfixes, which were behaviour tuning.

**This is a container-level failure, not a content-level one**, and the distinction is the useful
output of this cycle:

- *content staleness* — our override deletes developer changes — is what `verify_build.sh` checks
  [2]/[3]/[4] test, and it was genuinely absent.
- *container staleness* — our pak's script imports no longer resolve against the current global
  store — was never tested by anything, and is what actually broke.

Check [5] added earlier this cycle narrows the gap: it compares the live cook against
`build/framework/src`, so a stale build tree now shows up. It is still not a direct test of import
resolution. **The honest position is that no static check in this repo can currently prove a pak
loads.** Only launching the game does that, which is why P0 stays open until someone does.

> A cheap standing check falls out of this, and it needs no game launch and no usmap: compare
> `build/framework/src/scriptobjects.bin` against a fresh extraction from the live cook. If those
> differ, every pak built from that tree is suspect regardless of how clean its content is. Worth
> folding into check [5].

## The rebuild — done and statically verified, but NOT a fix

> The three verifications below are sound and still stand: they establish that the rebuilt pak
> carries exactly the bytes intended. They do not establish that it fixes anything. With respect to
> script imports the rebuild is a **null intervention** — 193 of 199 packages byte-identical to the
> July pak, identical import lists throughout.

Rebuilt on the live `25071553` cook:

```
FW_AES_KEY=... RETOC=... USMAP=... python tools/cmsf_framework.py --slots 32
```

The generator's own decode-back pass reports `rows=32/32 roster=32/32 st=32/32` on all six
characters, 0.57 MB, 3.0 KB per slot.

**The usmap problem was worked around, not ignored.** Gate 1b is red, and
`cmsf_framework.py` serialises through UAssetAPI against that map, so the build needed an
independent check that nothing was mis-serialised. Three, none of which trust the type map:

1. **The append is exactly the right size.** Every pawn `.uexp` came out at
   `live_src + 672 bytes` — the 32 CMSF `SkinChoices` entries, and nothing else. A stale schema
   would almost certainly have changed the length.
2. **The pak round-trips its payload byte-for-byte.** Converting the built pak back with
   `retoc to-legacy` (no usmap) and comparing against what was staged: **199 of 199 `.uexp`
   payloads identical.** The `.uexp` is the serialised property data, so every byte the pak
   carries is exactly what was intended. The `.uasset` headers all differ — first difference at
   byte 29, sizes changed — because retoc rebuilds the legacy package summary from zen structures.
   That is a property of the conversion, not a defect; the payload is what matters.
3. **`verify_build.sh` is fully green**, check [5] included: *"14 file(s) byte-identical to the
   live cook — the pak was built on THIS cook."*

Positive evidence that the skin-side type layout did not move, which is why the stale map was
survivable here: `DT_SkinUIData` is **byte-identical** July↔September, and the six pawn `.uexp`
files are unchanged in **length**. Unversioned serialisation is schema-order dependent, so a
changed layout would move offsets. The demonstrated staleness is in `FWWeaponDefinition`, a weapon
struct CMSF never touches.

**What this does NOT establish.** That it loads. The mechanism above is a *container* failure, and
none of the three checks tests import resolution — they test that the pak carries the bytes we
meant. Per the house rule this is **unverified in-game**, and the release bundle is deliberately
**not built**: a stale `dist/release/` zip is recoverable, a published broken one is not.
